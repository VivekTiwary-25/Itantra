PURPOSE
-------
This file is meant to let any capable LLM continue teaching Vivek the
iTantra architecture from absolute zero, while using the attached build
specification as the source of truth.

The learner is NOT assumed to know cryptography, networking, Android BLE,
DTNs, Noise, key derivation, signatures, HMAC, CBOR, or related concepts.

The goal is NOT merely to summarize the design. The goal is to build a
complete mental model of the design, slowly, without skipping technical
details.

SOURCE-OF-TRUTH RULE
--------------------
1. The complete iTantra v1 build specification is included verbatim later
   in this file.
2. Teach what the specification actually says.
3. Do not silently invent missing details.
4. If the specification leaves something undefined, say so explicitly.
5. Claude's audit corrections listed below are proposed corrections to the
   current build spec. When the relevant architecture section is reached,
   explain:
      a. what the original design says;
      b. how it works;
      c. what Claude identified as the problem;
      d. whether/why the correction is needed;
      e. exactly what changes in message format, verification, database,
         implementation, or claims.
6. Do not jump straight to the audit. The learner wants to understand the
   architecture first, and encounter each audit correction naturally when
   the corresponding concept is taught.

CLAUDE AUDIT BACKLOG TO INTEGRATE WHILE TEACHING
======================================================================

These are audit findings supplied after reviewing the build specification.
Do not front-load all of them. Explain them when their corresponding chunk
is reached.

1. ANOTHER TRUSTED CONTACT CAN FAKE THE SENDER
Current concern:
- Recipient processing says to verify the sender signature, but the inner
  message contains sender_signing_public_key and then separately resolves
  sender_node_id.
- A malicious already-trusted contact could potentially claim another
  sender_node_id while signing with their own included key if the
  implementation trusts the included key.

Correction:
- Ignore the message-supplied key for identity authentication.
- Resolve sender_node_id to the stored trusted contact.
- Verify with that contact's previously authenticated stored signing key.
- Require the pair-secret/destination-tag match to correspond to the same
  trusted contact as sender_node_id.

Impact:
- Verification semantics change.
- No new wire field is required.

2. DESTINATION TAG IS THE SAME IN BOTH DIRECTIONS
Current concern:
- Both members of a trusted pair derive the same pair_secret.
- destination_tag currently depends only on pair_secret and bundle_id.
- Therefore a phone can match its own outgoing messages when later seeing
  them in another relay's inventory.

Proposed correction:
- Bind direction / intended recipient into the tag input, e.g.
  HMAC(pair_secret,
       "itantra-v1/destination-tag" || recipient_node_id || bundle_id)
- Bind both public keys, sorted deterministically, into HKDF info.
- Check the X25519/library return code and reject invalid/all-zero shared
  secret results.

Impact:
- Wire format / derivation semantics change before Phase 4.

3. OUTER ENVELOPE IS NOT PROTECTED END TO END
Current concern:
- Signature covers only the inner message.
- Relay-visible fields such as lifetime, priority, and deletion_commitment
  can be modified by a malicious relay.
- A modified deletion_commitment can make legitimate future tombstones fail.

Proposed correction:
- Put bundle_id, deletion_commitment, lifetime, and priority inside the
  signed inner message as authenticated copies.
- Recipient checks they match the outer envelope.
- Relays still cannot verify those bindings because they cannot decrypt;
  document this limitation.

Impact:
- Private-message wire format changes.

4. DEDUPLICATION BY bundle_id ALONE CAN BLOCK THE REAL MESSAGE
Current concern:
- bundle_id is visible.
- An attacker can reuse a visible bundle_id on garbage ciphertext.
- If a node marks the ID seen before validating the real object, the valid
  bundle can be discarded later.

Proposed correction:
- Relay dedupe uses bundle_id + ciphertext_hash.
- Recipient marks delivery seen only after successful decryption,
  recipient check, and signature authentication.
- Recipient-level dedupe uses inner_message_id.

Impact:
- Database/deduplication key changes.

5. SOME SIGNATURE TYPES LACK DOMAIN SEPARATION
Affected objects called out by the audit:
- Identity capsule
- Delivery receipt
- SOS request
- SOS cancellation

Correction:
Give each signed object a fixed type/domain prefix, e.g.
- "itantra-v1/capsule"
- "itantra-v1/receipt"
- "itantra-v1/sos-request"
- "itantra-v1/sos-cancel"

Why:
A signature valid for bytes in one protocol context should not be
reinterpretable as a signature for another object type.

Impact:
- Signature semantics / QR interoperability can change.
- Capsule fix should happen before Phase 1.

6. RELAY NOISE XX STATIC KEY IS UNSPECIFIED
Current concern:
- Noise XX exchanges static public keys during the handshake.
- Reusing long-term iTantra identity keys would reveal a stable identity
  to every stranger relay.

Proposed correction:
- Relay sessions use fresh random Noise static keys per Emergency-mode
  session.
- Long-term identity keys never enter stranger-relay Noise sessions.
- SOS trust State 2 short authentication string should be derived from the
  Noise handshake hash.

Impact:
- Mostly implementation semantics, not the private-bundle format.

7. BLE ADVERTISEMENT DOES NOT CONTAIN THE ID NEEDED BY §8
Current concern:
- Connection collision logic compares peer_session_id.
- Existing advertisement layout does not include it.
- Legacy BLE advertising space is very small.

Proposed v1 layout:
- One service-data field under the iTantra 128-bit UUID containing:
    1 byte protocol version
    1 byte flags
    8-byte rotating random short ID
- Do not separately include device name or TX power.
- Rotate the short ID periodically.
- Explicitly set include-device-name = false and include-TX-power = false.

Impact:
- Advertisement format changes before Phase 2.

8. AGE COUNTER BREAKS ACROSS DEVICE REBOOT
Current concern:
- SystemClock.elapsedRealtime() resets on reboot.
- Stored pre-reboot bundles cannot continue age correctly from only
  received_age_ms + (elapsedRealtime_now - received_elapsed_ms).

Proposed correction:
- Store Android boot count with each bundle.
- Periodically persist current accumulated age.
- If boot count changes, resume from the last persisted age rather than
  subtracting elapsedRealtime values from different boots.

Impact:
- Adds database/persistence state.

9. NOISE LIBRARY FEASIBILITY MUST BE DECIDED BEFORE PHASE 3
Audit concern:
- Mature/maintained Android-native Noise options may be limited.
- An old Java library may be stale.
- Rust snow via JNI introduces NDK/JNI and may violate current lane rules.
- Building Noise manually from crypto primitives is a redesign and should
  not be done casually.

Required team decision:
- Pick and pin a reviewed library path before Phase 3.
- If JNI/NDK is required, explicitly escalate that architectural/build
  change.

ADDITIONAL PHASE-SPECIFIC AUDIT NOTES
-------------------------------------
A. Copy tokens can temporarily overcount after interrupted transfer:
   sender may not receive the receiver's acknowledgement after receiver
   already persisted a copy. Reconciliation on future encounters is needed.
   Acceptance wording should not claim perfect budget preservation under
   interruption.

B. Delivery receipts:
   - must include inner_message_id;
   - must never themselves trigger delivery receipts.

C. Multiple SOS responders:
   two responders may accept nearly simultaneously.
   Define first confirmed accept as winner; suppress/notify later accepts.

D. Sybil limitation:
   a stranger controlling multiple fake identities can consume spray copies.
   This should be explicitly listed under limitations.

E. Message length leakage:
   ciphertext size leaks approximate plaintext size.
   Proposed mitigation: pad into fixed buckets such as
   256 B, 1 KiB, 4 KiB, 16 KiB.

F. Android Auto Backup:
   wrapped private-key files should be excluded from backup because the
   Keystore wrapping key will not survive a restore onto a new install/device.
   UI should explain that reinstalling loses identity and requires QR
   re-exchange.

G. Trim SOS for v1:
   remove "credential-present" and trust State 3 from the build-critical path.
   Keep responder credentials as future work unless explicitly re-added.

H. Android/BLE implementation gotchas:
   - Screen-off BLE scanning requires filters.
   - Avoid restarting scans repeatedly; Android can suppress excessive starts.
   - GATT operations must be serialized through a queue.
   - Retry transient GATT failures such as status 133 with bounded backoff.
   - Test simultaneous GATT client/server operation on real target devices.
   - Realme/OEM background restrictions require explicit long-duration
     screen-off testing and possibly battery-optimization exemption guidance.

0. AUDITOR INSTRUCTION

Before implementation, audit this specification for:

- cryptographic mistakes;
- authentication confusion;
- metadata leaks;
- replay/downgrade attacks;
- unsafe trust transitions;
- incorrect Noise usage;
- incorrect key derivation or domain separation;
- Android BLE/GATT feasibility issues;
- concurrency/state-machine bugs;
- denial-of-service opportunities;
- persistence/routing inconsistencies;
- situations where a UI claim is stronger than the protocol guarantee.

Do not silently redesign the architecture.

For every issue found, report:
1. the exact problematic requirement;
2. why it is wrong or risky;
3. exploit/failure scenario;
4. minimum correction;
5. whether the correction changes interoperability or stored data.

Crypto primitives MUST come from maintained, reviewed libraries. No cryptographic primitive may be implemented manually.

1. PRODUCT DEFINITION

iTantra provides exactly two user-facing communication modes.

Mode A — Trusted Person

Example:
Send Rahul: I am safe. Meet me at the shelter.

Rahul is already a trusted iTantra contact.
The sender already possesses Rahul's authenticated cryptographic identity.

The message:
- is encrypted specifically for Rahul;
- may travel through arbitrary stranger phones;
- may remain stored on relay phones;
- may move over several physical encounters;
- remains unreadable to those relays;
- eventually reaches Rahul if network mobility permits;
- is considered Delivered only after authenticated recipient confirmation.

Rahul does not need to be nearby when the message is created.

Mode B — SOS

Example:
I need a human right now.

There is no intended identity.

iTantra:
1. finds nearby participating phones;
2. attempts contact with a small number of nearby candidates;
3. establishes an encrypted session with a responder;
4. labels the responder as unverified unless additional authentication occurs;
5. expands the SOS if nobody nearby responds.

The security statement before authentication is:
Encrypted connection — identity not verified.

Not:
Secure person.
Trusted helper.
Nearest person.

2. NON-GOALS

v1 does NOT attempt to provide:
- discovery of an arbitrary unknown person by name;
- private offline "find Rahul" lookup;
- one-person-one-identity Sybil resistance;
- exact physical-distance measurement;
- guaranteed nearest-helper selection;
- guaranteed message delivery;
- guaranteed cooperation from relays;
- traffic-analysis resistance;
- global anonymity;
- thousands-device validated scalability;
- standardized Bluetooth Mesh;
- BPv7 interoperability;
- blockchain/DID-based outage naming;
- global reputation scores;
- self-designed cryptography.

If Rahul is not already a trusted contact, Trusted Person mode refuses to address him.
The appropriate alternative is SOS.

4. FROZEN TRANSPORT DECISION

4.1 Discovery

BLE advertising + BLE scanning is mandatory.

BLE discovery answers:
Which iTantra phones are physically reachable right now?

Advertisements MUST NOT expose:
- user's name;
- phone number;
- contact list;
- long-term cryptographic fingerprint;
- message contents.

Advertising contains only:
- iTantra service UUID;
- protocol major version;
- capability flags;
- SOS-active flag where applicable.

RSSI may be recorded as a rough contact-quality signal only.

It MUST NOT be converted into claims such as:
2.4 metres away.
or:
closest human.

5. BYTE TRANSPORT

Canonical v1 transport:
BLE GATT

All functionality required by v1 MUST work using BLE GATT alone.

Reasons:
- supports unpaired application communication;
- supports stranger SOS;
- supports small encrypted text/control bundles;
- does not require infrastructure;
- permits app-layer Noise encryption.

Optional adapter:
Existing RFCOMM code may be preserved behind the same abstraction.

RFCOMM may be used when:
- devices are already paired;
- the connection exists;
- using it improves transfer reliability.

RFCOMM MUST NOT be required for SOS.

Unpaired insecure RFCOMM MUST NOT be treated as secure unless protected by the same application-layer cryptographic session.

Deferred transports:
- Wi-Fi Aware;
- Wi-Fi Direct;
- Nearby Connections;
- RTT/UWB;
- automatic multi-radio negotiation.

The architecture MUST nevertheless make adding them possible later.

6. TRANSPORT ABSTRACTION

Implement:

interface PeerLink {
    val peerSessionId: ByteArray
    val state: State

    suspend fun connect()
    suspend fun send(frame: ByteArray)
    fun incomingFrames(): Flow<ByteArray>
    suspend fun close()
}

Implement initially:

PeerLink
 ├── BleGattPeerLink        REQUIRED
 └── RfcommPeerLink         OPTIONAL / adapt existing implementation

Nothing above PeerLink may depend directly on BluetoothGatt, BluetoothSocket, Wi-Fi APIs, MAC addresses, or transport-specific IDs.

A message must be able to travel:
A --GATT--> B --future transport--> C --GATT--> Rahul

without changing the DTN message format.

7. BLE GATT PROFILE

Use one custom iTantra GATT service.

Conceptually:

iTantraService
 ├── ClientToServer
 │      WRITE_WITH_RESPONSE
 │
 └── ServerToClient
        INDICATE

Use application-level fragmentation because GATT MTU varies.

Each fragment includes:
fragment_version
connection_session_id
frame_id
fragment_index
fragment_count
payload_fragment

Requirements:
- hard maximum frame length;
- hard maximum fragment count;
- reject conflicting fragments;
- reject duplicate malformed fragments;
- reassembly timeout;
- memory cap per peer;
- frame hash or authenticated Noise framing detects corruption.

A completed application frame is passed upward only after full reassembly.

8. PEER CONNECTION COLLISION

Both phones may discover each other simultaneously.

Each Emergency-mode instance therefore generates a random temporary:
peer_session_id = random 128 bits

After discovering each other, a deterministic connection rule prevents both phones continuously attempting to become client.

Example rule:
smaller peer_session_id initiates connection
larger peer_session_id waits

If no connection appears within a bounded retry period, roles may be retried.

This identifier is temporary and MUST NOT be the user's identity.

9. HOP SECURITY

Every established PeerLink runs an application-layer secure session.

For unknown relay peers:
Noise XX

The Noise implementation MUST come from a reviewed library.
Do not implement Noise manually.

The hop security layer protects:
- inventory;
- bundle transfers;
- SOS offers;
- protocol negotiation;
- control frames

from ordinary passive radio observers.

A relay remains untrusted even after Noise succeeds.

Noise XX means:
I have an encrypted connection to whoever controls the key participating in this handshake.

It does NOT mean:
I know who this human is.

10. IDENTITY

Each installation generates two long-term identity keys:

Ed25519
    signing / identity authentication

X25519
    end-to-end message encryption / pairwise secret derivation

Private keys MUST NOT be stored directly in SharedPreferences, Room, files, logs, or source code.

If the required primitive can be securely stored directly using Android Keystore, do so.

Otherwise:
1. generate key material using a cryptographically secure RNG;
2. store it encrypted;
3. protect the wrapping key using Android Keystore.

Do not claim hardware-backed protection unless runtime verification proves it.

11. IDENTITY CAPSULE

A user's shareable identity object:

IdentityCapsuleV1 {
    version
    signing_public_key
    encryption_public_key
    display_name_hint
    key_epoch
}

The capsule is self-signed using the Ed25519 private key.

Its cryptographic identifier is derived from the key material, not from the display name.

Conceptually:

node_id =
Trunc128(
    SHA256(
        "itantra-v1/node-id" ||
        signing_public_key ||
        encryption_public_key
    )
)

The display name is never treated as identity.

12. TRUSTED CONTACT CREATION

v1 uses QR-based contact exchange.

Flow:

Rahul
  ↓
Show My iTantra QR
  ↓
Vivek scans QR
  ↓
capsule signature verified
  ↓
fingerprint shown
  ↓
Vivek explicitly confirms
  ↓
Rahul stored as TRUSTED CONTACT

Contact database stores:
local_name = "Rahul"
node_id
signing_public_key
encryption_public_key
fingerprint
trust_method = QR_VERIFIED
created_at

A user-facing contact name may be edited without changing cryptographic identity.

13. TRUST RULE

Trusted Person mode MUST NOT send based solely on:
- display name;
- Bluetooth device name;
- Android device name;
- phone number;
- MAC address;
- discovered BLE peer ID.

The selected contact must resolve to exactly one stored trusted capsule.

If not:
Cannot securely identify this recipient.

Do not guess.

14. PAIRWISE DESTINATION SECRET

We do not expose Rahul's stable cryptographic identifier to relay phones.

For each pair of trusted users derive:

shared =
X25519(
    own_encryption_private_key,
    contact_encryption_public_key
)

pair_secret =
HKDF-SHA256(
    shared,
    info = "itantra-v1/pair-secret"
)

Never transmit pair_secret.

15. PER-MESSAGE DESTINATION TAG

Every private bundle receives a random:
bundle_id = random 128 bits

Its opaque destination tag is:

destination_tag =
Trunc128(
    HMAC-SHA256(
        pair_secret,
        "itantra-v1/destination-tag" || bundle_id
    )
)

Properties intended by this construction:
- different messages produce different tags;
- relays cannot convert a tag into "Rahul";
- no stable recipient identifier is broadcast;
- Rahul can recognize a message generated by one of his trusted contacts.

Recipient matching:

for contact in trustedContacts:
    candidate =
        HMAC(pair_secret(contact), domain || bundle_id)

    if candidate == destination_tag:
        this bundle may be for me

Then attempt authenticated decryption.

AUDIT THIS CONSTRUCTION CAREFULLY.

In particular review:
- HKDF salt/info;
- HMAC domain separation;
- cross-protocol key reuse;
- contact-count scaling;
- active probing;
- compromise implications.

16. PRIVATE MESSAGE FORMAT

All structured protocol data uses deterministic/canonical CBOR.

A private message has two layers.

Relay-visible envelope:

PrivateBundleV1 {
    immutable {
        protocol_version
        bundle_id
        destination_tag
        lifetime_ms
        priority
        deletion_commitment
        ciphertext_hash
        ciphertext
    }

    relay_state {
        copy_tokens
        hop_count
        accumulated_age_ms
    }
}

Relays may see:
- bundle ID;
- opaque destination tag;
- ciphertext size;
- coarse priority;
- remaining age/lifetime;
- copy tokens;
- hop count;
- deletion commitment.

Relays MUST NOT see:
- Vivek;
- Rahul;
- phone numbers;
- contact names;
- plaintext;
- exact location;
- sender fingerprint;
- recipient fingerprint.

17. INNER PRIVATE MESSAGE

Generate:
inner_message_id = random 128 bits
deletion_secret = random 256 bits

Payload:

PrivateMessageV1 {
    protocol_version
    inner_message_id
    sender_node_id
    recipient_node_id
    sender_signing_public_key
    language
    text
    created_time_hint
    deletion_secret
}

Sender signs the canonical representation:

signature =
Ed25519.Sign(
    "itantra-v1/private-message" ||
    CanonicalCBOR(PrivateMessageV1)
)

Then:

SignedPrivateMessageV1 {
    message
    signature
}

18. END-TO-END ENCRYPTION

For v1 use a mature implementation of an X25519-based recipient-only sealed-box construction.

Conceptually:

ciphertext =
SealedBox(
    recipient_X25519_public_key,
    CanonicalCBOR(SignedPrivateMessageV1)
)

The sender's Ed25519 signature inside the encrypted object provides sender authentication to Rahul after decryption.

Do not create a custom ECDH + AES construction.

If the auditor recommends a mature HPKE implementation instead, the substitution is acceptable only if the complete envelope and authentication semantics are documented.

Forward secrecy for old stored messages after recipient long-term-key compromise is not guaranteed in v1.

X3DH / prekeys / Double Ratchet are future work.

19. DELETION COMMITMENT

Before encryption:
deletion_secret = random 256 bits

deletion_commitment =
SHA256(
    "itantra-v1/delete" ||
    deletion_secret
)

deletion_secret stays inside the encrypted private message.
deletion_commitment is stored in the outer bundle.

Therefore relays know the commitment but not the secret.

20. BUNDLE PERSISTENCE

Every accepted relay stores the entire bundle before acknowledging receipt.

Storage must be durable across:
- app backgrounding;
- app process death;
- screen lock;
- normal application restart.

Room is appropriate for bundle metadata/state.
The encrypted bundle bytes may be stored as a BLOB/file-backed payload.

Relay acknowledgement means:
I persisted these bytes.

It does NOT mean:
I promise they will reach Rahul.

21. BUNDLE LIFECYCLE

Sender UI states:

QUEUED
    stored only locally

RELAYED
    at least one relay accepted a copy

DELIVERED
    authenticated recipient receipt received

EXPIRED
    bundle lifetime elapsed without delivery

UNKNOWN
    state continuity lost

Never display:
Sent to Rahul
merely because a relay accepted it.

22. DEFAULT ROUTING PARAMETERS

URGENT_PRIVATE_COPY_BUDGET = 8
NORMAL_PRIVATE_LIFETIME = 24 hours

23. BINARY SPRAY-AND-WAIT

Each private bundle begins with L copy tokens.

Example:

A owns 4
A meets B
A keeps 2
B receives 2

B meets C
B keeps 1
C receives 1

Transfer rule when:
copy_tokens > 1

Sender:
keeps ceil(n / 2)

Receiver:
gets floor(n / 2)

When:
copy_tokens == 1

the node waits for a peer claiming destination match.

It does not spray the last relay token arbitrarily.

24. INVENTORY EXCHANGE

Once Noise is established, peers exchange bounded inventories before sending payloads.

Example summary:

BundleSummary {
    bundle_id
    destination_tag
    bundle_kind
    coarse_priority
    remaining_lifetime
    payload_size
    copy_tokens
}

Inventory MUST be:
- paginated;
- size bounded;
- filtered to nonexpired objects;
- free of plaintext.

Receiver responds with requested bundle IDs.

Possible request modes:
WANT_RELAY
WANT_DESTINATION

25. DESTINATION RECOGNITION

A peer receiving inventory attempts destination-tag matching using its trusted contacts.

If a match is found:
WANT_DESTINATION(bundle_id)

A relay cannot cryptographically prove that the peer is telling the truth at this stage.

Therefore:
A destination claim never causes the existing copy to be deleted.

A destination attempt receives a delivery copy.

The holder retains its own copy until:
- valid tombstone;
- authenticated delivery receipt where applicable;
- expiry;
- storage eviction policy.

A malicious phone claiming "I am destination" can therefore waste transfer bandwidth but cannot cause the last honest copy to disappear merely by claiming destination status.

Rate-limit destination claims.

26. RECIPIENT PROCESSING

Rahul receives the encrypted bundle.

He:
1. decrypts using his X25519 private key;
2. parses canonical CBOR;
3. verifies sender Ed25519 signature;
4. verifies recipient_node_id == own node_id;
5. resolves sender_node_id against trusted contacts;
6. checks inner message ID for duplicate delivery;
7. stores the message once;
8. shows / speaks it once.

If signature or destination checks fail:
DROP

Do not generate a delivery receipt.

27. DUPLICATION

Maintain:
SeenBundleStore

keyed by:
bundle_id

Receiving the same bundle again MUST NOT:
- show the message again;
- reset expiry;
- increase copy budget;
- generate repeated user notifications.

Seen state survives app restart and lasts at least until bundle expiry plus grace period.

28. DELIVERY TOMBSTONE

After successful recipient decryption:
Rahul learns deletion_secret.

He produces:

TombstoneV1 {
    protocol_version
    ack_of_bundle_id
    deletion_secret
    remaining_lifetime
}

A relay that possesses the original bundle verifies:

SHA256(
    "itantra-v1/delete" ||
    deletion_secret
)
==
stored deletion_commitment

If valid:
delete stored bundle
store tombstone marker

The tombstone prevents the bundle being reaccepted.

A node SHOULD propagate the tombstone only if it has evidence of the corresponding bundle/seen entry.

29. AUTHENTICATED DELIVERY RECEIPT

Rahul separately creates a signed end-to-end receipt:

DeliveryReceiptV1 {
    ack_of_bundle_id
    recipient_node_id
    status = DELIVERED
    receipt_time_hint
}

Rahul signs it with Ed25519.

The receipt is encrypted to the original sender and routed as a small private DTN bundle.

Only after verifying Rahul's signature may the sender UI transition:
RELAYED → DELIVERED

Tombstone and delivery receipt are intentionally separate:

Tombstone:
    helps relays clean storage.

Delivery receipt:
    proves to sender that Rahul accepted it.

30. EXPIRY

Each relay stores:
received_accumulated_age_ms
received_at_elapsedRealtime

Current effective age:

received_accumulated_age_ms
+
(SystemClock.elapsedRealtime() - received_at_elapsedRealtime)

When forwarding, transmit the updated age.

If:
effective_age >= lifetime

delete bundle and retain only whatever short dedupe record is required.

Wall-clock UTC MUST NOT be the sole expiry mechanism.

31. STORAGE PRESSURE

Eviction priority:
1. expired objects
2. already tombstoned objects
3. low-priority normal bundles
4. older normal bundles
5. urgent bundles
6. active SOS traffic last

Never delete a sender's only remaining copy merely because another relay previously accepted the message.

Storage caps MUST exist globally and per observed origin/session.

40. MULTI-HOP SOS REQUEST

iTantra can send end-to-end encrypted messages to previously trusted contacts through untrusted intermediary phones.

Relay devices carry ciphertext and do not require access to message plaintext.

iTantra uses application-layer store-carry-forward, so the final recipient does not need to be within radio range of the sender when the message is created.

Replication is bounded rather than unrestricted flooding.

Nearby strangers can establish an encrypted SOS conversation without a prior trust relationship.

iTantra distinguishes encrypted communication from verified human identity.

64. CLAIMS WE MUST NOT MAKE

Do not claim:
All relays are trusted.
Every message will arrive.
SOS always finds the nearest human.
Noise XX proves who the stranger is.
BLE RSSI proves physical distance.
iTantra prevents Sybil attacks.
A responder credential is guaranteed currently unrevoked while offline.
iTantra is Bluetooth Mesh.
Thousands of phones have been validated.
Message metadata is completely hidden.
The cryptography is formally verified.
