4.7 Preprocessor / deployment audit
-----------------------------------
Concern:
working model used preprocessor.ts, which looked like it might force PyTorch/TorchScript onto Android.

Audit result:
NO HARD BLOCKER.

preprocessor.ts contains no learned weights and no training-only magic.

It performs:
- pre-emphasis 0.97
- reflect pad 256 each side
- STFT
  n_fft=512
  hop=160
  Hann window=400
- power spectrum
- 80-band Slaney mel filterbank, 0–8 kHz
- log(x + 2^-24)
- per-feature mean/std normalization over time
  N-1 variance
  +1e-5 std stabilization

Output:
(80, T)
T = L//160 + 1

Sherpa already has a NeMo CTC-style feature frontend.
The desktop audit found sherpa features close enough and preserved aggregate WER.
An 80-sample reflected prefix improved feature alignment on desktop but later gave no benefit on the actual phone.

Conclusion:
Do NOT drag PyTorch onto Android.
Use sherpa frontend.

4.10 Multilingual shared architecture
-------------------------------------
This is the latest STT architecture result.

The goal:
avoid 9 × ~657 MB fused models.

Original model language structure discovered:
- encoder is language-agnostic
- head is one shared 1x1 Conv with 5633 rows
- 22 languages × 256 token rows
- + 1 shared blank row at global index 5632
- each language uses its own 256 rows + the shared blank
- local output size 257
- local blank id 256

Desired iTantra languages:
hi, gu, mr, kn, ml, ta, te, or, bn

Four options tested:

OPTION A
shared encoder + separate tiny head ONNX
- technically clean
- bit-exact
- head switch 2–3 ms
- BUT sherpa cannot directly run split model this way without custom glue

OPTION B
one ONNX with lang_id input
- works in ORT
- sherpa fails because it only feeds expected inputs and not extra lang_id

OPTION C — CHOSEN CURRENTLY
thin sherpa-compatible per-language wrappers referencing ONE shared external weight file
- no custom native code
- one large physical encoder copy on disk
- works with sherpa
- Hindi bit-exact vs known-good fused model
- downside: switching language reloads encoder/session

OPTION D
custom native adapter
- would enable keeping encoder resident and swapping small heads
- needs Kotlin/native/JNI/ORT integration
- estimated 1–2 days
- not chosen yet

Option C storage:
Shared INT8-B encoder weights:
~651.95 MB

Encoder graph:
~4 MB

Per language:
~1.05 MB head slice + ~2.8 KB tokens
but practical wrapper overhead makes each extra language ~5.05 MB total.

Total all 9:
~697.42 MB

Bad architecture:
9 × fused models ~5912.49 MB

Saving:
~5215 MB
~88.2%

IMPORTANT:
This shares storage, NOT active session RAM.

Current language switch behavior:
release recognizer
→ construct selected <lang>.onnx wrapper
→ reload same shared encoder weights

Desktop reload:
~2.3 s

Expected phone switch:
around previous 3–4 s ballpark, but this exact external-data multilingual package has NOT yet been run on Android.

Two simultaneous recognizers:
~1.3 GB desktop private memory
So do not keep two alive.

Option A would avoid reload, but requires custom integration.
