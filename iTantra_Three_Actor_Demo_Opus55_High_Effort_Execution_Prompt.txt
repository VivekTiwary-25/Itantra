ITANTRA SIH — THREE-ACTOR DEMO BUILD
GINORMOUS EXECUTION PROMPT FOR CLAUDE OPUS 5.5 — HIGH EFFORT

You are operating inside the iTantra Android repository. This is an EXECUTION task, not a design essay, not a code review, not a capability audit, and not a request for a speculative plan.

Your job is to inspect the current checkout, understand the real project structure, then IMPLEMENT a polished, deterministic, film-ready Android UI demo as THREE DEDICATED ACTOR APPS/APKs:

1. VACHANA DEMO APP
2. YASH DEMO APP
3. VIVEK DEMO APP

These are three dedicated role-specific demo builds, but DO NOT create three separate codebases. Reuse shared components, state, navigation, styling, and demo infrastructure aggressively. The preferred architecture is three product flavors/build variants with role-specific configuration, application IDs, defaults, and reachable flows. If the repository already has a better equivalent mechanism, use it, but the result must still be three independently buildable/installable actor-specific APKs.

The film editor will stitch clips together. THERE IS NO REQUIREMENT FOR THE THREE PHONES TO ACTUALLY COMMUNICATE WITH EACH OTHER DURING FILMING.

That is a fundamental constraint.

The purpose of these demo builds is deterministic UI capture. A send on Vachana's phone does not need to cause an event on Yash's phone. A reply on Yash's phone does not need to reach Vachana's phone. Vivek does not need to actually discover Vachana's SOS over radio. Each actor app can locally simulate the state needed for its own shot, on a controllable timer, and the edit supplies continuity.

The real iTantra networking/speech code may remain intact in the repository. Do not destroy it. Do not perform giant refactors of backend systems. Isolate demo-only behavior cleanly so it is obvious that these are demo builds.

The most important implementation principles are:

- Make the UI look finished and intentional.
- Make filming deterministic.
- Reuse components ruthlessly.
- Prefer local demo state over flaky Bluetooth/STT/TTS dependencies for these filmed paths.
- Do not expose developer-looking diagnostic screens in the filmed UI.
- Do not make the filmed flow depend on real STT, real TTS, real Bluetooth delivery, or real QR trust establishment.
- Use real Android system notifications so the notification footage looks native.
- Use hidden/demo-only controls to configure the next filmed event.
- Keep the number of unique screens/components low.
- Build and test the three APKs on the actual project, not in a web mockup.
- Do not merely describe changes. Make them.

25A. MANDATORY REMOTE PUBLISH STEP — REPO-BACKED APK DELIVERY
===============================================================================

The user's phones do NOT need to remain connected to the development machine.

After every successful final build, you MUST publish the three actor APKs to the repository's remote so they can be downloaded later.

Preferred publication mechanism:
GITHUB RELEASE ASSETS associated with the current repository.

Why:
- do not bloat normal git history with APK binaries
- APKs may be too large for ordinary GitHub file limits
- release assets are easy to download onto a phone
- each actor can retrieve only the APK they need

Inspect the repository's `origin` remote and current authentication.

If the remote is GitHub and the GitHub CLI (`gh`) is installed/authenticated:

1. Build all three APKs successfully.
2. Copy/rename successful artifacts to stable filenames:
   - iTantra-Vachana-latest.apk
   - iTantra-Yash-latest.apk
   - iTantra-Vivek-latest.apk
3. Compute SHA-256 for each.
4. Create or update a dedicated rolling release/tag:
   - tag: demo-latest
   - title: iTantra SIH Demo — Latest
5. Upload the three APKs to that release using overwrite/clobber behavior where supported.
6. Also include a tiny text manifest containing:
   - build timestamp
   - git commit SHA
   - actor/app variant
   - APK SHA-256
7. Do not publish failed or partially built artifacts.
8. Only replace a prior "latest" APK after the new APK for that actor has built successfully.
9. Push the source-code branch/commits normally before or alongside publishing the release.
10. Report the final repository remote, release/tag, asset names, and commit SHA.

If `gh` is unavailable or unauthenticated but ordinary `git push` works:
- DO NOT silently skip remote delivery.
- First try to discover whether another existing authenticated repository-release mechanism is available.
- If none is available, use a dedicated artifact branch ONLY as a fallback:
  - branch: demo-apks
  - keep only the current latest APKs + manifest in the working tree
  - use stable names above
  - avoid polluting the main/source branch with binary APK commits
  - force-updating the dedicated artifact branch is acceptable ONLY if necessary to keep it rolling and isolated, and only after preserving source work on its normal branch
- Be aware of host binary-size limits. If an APK exceeds the remote's file limit, do not pretend upload succeeded; report the exact blocker and prefer release assets.

Never require a phone to be connected for the final delivery step.

The final definition of "done" is:
SOURCE CHANGES COMMITTED/PUSHED
+ ALL THREE APKS BUILT
+ ALL THREE APKS PUBLISHED REMOTELY
+ DOWNLOAD LOCATION/RELEASE IDENTIFIED

If remote publication fails due authentication/permissions, continue to preserve all successful local builds and source commits, then report the exact command/error and the local APK paths. Do not claim completion of remote delivery.
